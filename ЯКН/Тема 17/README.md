# Обектно-ориентирано програмиране: Подтипов и параметричен полиморфизъм. Множествено наследяване

> Подробни обяснения по конспекта за държавен изпит по Компютърни науки. Примерите са на C++ без използване на `std::string` и стандартни контейнери — работим директно с указатели, динамична памет и `char*` низове.

---

## 0. Какво е полиморфизъм и защо ни е?

**Полиморфизъм** ("много форми") е свойството на даден елемент от програмата (тип, функция, операция) да приема повече от една форма.

В C++ имаме **три вида полиморфизъм**:

1. **Ad-hoc (претоварване на функции)** — една и съща функция има различни реализации в зависимост от типовете на параметрите. Например `Rational operator+(Rational, Rational)` и `int operator+(int, int)` — изборът става по време на компилация (статично).

2. **Параметричен полиморфизъм (шаблони)** — *една и съща* реализация работи унифицирано за много различни типове. Например `template <typename T> void swap(T&, T&)`.

3. **Подтипов полиморфизъм (виртуални функции)** — една и съща *сигнатура* се реализира различно от всеки подклас в йерархия от наследявания. Например `void Player::print() const` се преопределя в `Hero::print()`, `Bot::print()` и т.н.

**Защо ни е?** По същата причина, поради която ни е цикъл — искаме да обработваме много сходни обекти **унифицирано**, с един и същи код, без да дублираме логиката.

## 1. Виртуални функции и подтипов полиморфизъм

### 1.1. Статично срещу динамично свързване

Когато компилаторът види извикване на функция, той трябва да реши **коя точно реализация** да бъде извикана. Този процес се нарича **свързване (binding)**:

- **Статично свързване (early binding)** — изборът се прави по време на **компилация**. Компилаторът гледа *статичния* тип на променливата/указателя и избира съответната функция. По подразбиране в C++ свързването е статично.
- **Динамично свързване (late binding)** — изборът се прави по време на **изпълнение** на програмата. Изпълнявайки кода, програмата гледа *динамичния* тип на обекта (т.е. от какъв точно клас е реалният обект, към когото сочи указателят) и избира съответния метод.

Пример защо това е важно:

```cpp
class Player {
public:
    void print() const {
        // ... извежда основна информация
    }
};

class Hero : public Player {
public:
    void print() const {
        // ... извежда информация специфична за герой
    }
};

Player* pp = new Hero;
pp->print();  // ???
```

**Какъв е въпросът?** Кой `print()` ще се извика — `Player::print()` или `Hero::print()`?

- **Статичен тип на `pp`**: `Player*` (това е, което компилаторът вижда)
- **Динамичен тип**: `Hero*` (това е реалният обект в паметта)

При **статично свързване** ще се извика `Player::print()` — компилаторът избира по статичния тип. Това **не е** това, което искаме!

### 1.2. Виртуални член-функции

За да укажем, че искаме динамично свързване, използваме ключовата дума `virtual`:

```cpp
class Player {
public:
    virtual void print() const {
        // ... основна информация
    }
};

class Hero : public Player {
public:
    void print() const override {  // override не е задължително, но е добра практика
        // ... информация за герой
    }
};

Player* pp = new Hero;
pp->print();  // СЕГА извиква Hero::print() — динамично свързване!
```

**Терминология:**
- Функция с динамично свързване се нарича **виртуална**.
- Клас, който има поне една виртуална функция, се нарича **полиморфен**.

### 1.3. Кога имаме статично и кога динамично свързване

Това е ключово за интуицията. Дори да сме сложили `virtual`, не винаги имаме динамично свързване!

| Извикване | Свързване | Защо |
|-----------|-----------|------|
| `Player p; p.print();` | статично | Типът се знае предварително, обектът е точно `Player` |
| `Player* pp = &h; pp->print();` | **динамично** | Указателят може да сочи към обект-наследник |
| `Player& ap = h; ap.print();` | **динамично** | Препратката е еквивалентна на указател |
| `Player::print();` | статично | Изрично сме указали кой метод |
| Извикване от друг метод: `this->print()` | **динамично** | `this` е указател |
| Извикване от **конструктор** на основен клас | статично | Обектът-наследник още не е построен! |
| Извикване от **деструктор** на основен клас | статично | Обектът-наследник вече е разрушен! |

**Интуиция:** динамично свързване се случва само през указател или препратка (защото те могат да сочат към "нещо различно"). Когато имаме директен обект — типът се знае и няма какво да се определя по време на изпълнение.

### 1.4. Особености на виртуалните функции

- Само **член-функции** могат да бъдат виртуални (обикновени функции — не).
- **Конструкторите не могат да са виртуални** — те се извикват "преди" обектът да е създаден напълно, така че няма как да се избере "правилен" конструктор по тип на обект.
- Наследяващата член-функция в производния клас трябва да е със **същата сигнатура** (същото име, същите параметри, същите `const` модификатори). Ако сигнатурата е различна, за C++ това е *друга* функция и динамичното свързване не работи.
- Наследяващите функции автоматично стават виртуални — `virtual` може да се пропусне, но е добра практика да слагаме `override`, за да се пази компилаторът да ни помогне.

### 1.5. Виртуални деструктори — критично важно!

Разгледайте следния код:

```cpp
class Player {
    char* name;  // динамична памет!
public:
    Player(const char* n) {
        name = new char[strlen(n) + 1];
        strcpy(name, n);
    }
    ~Player() { delete[] name; }
};

class Bot : public Player {
    char* algorithm;  // динамична памет!
public:
    Bot(const char* n, const char* alg) : Player(n) {
        algorithm = new char[strlen(alg) + 1];
        strcpy(algorithm, alg);
    }
    ~Bot() { delete[] algorithm; }
};

Player* pp = new Bot("R2D2", "minimax");
delete pp;  // ???
```

Какъв деструктор ще се извика при `delete pp`?

- **Без `virtual`**: статично свързване → извиква се само `~Player()`. Полето `algorithm` от `Bot` НИКОГА не се освобождава → **изтичане на памет**!

Решение: правим деструктора виртуален:

```cpp
class Player {
public:
    virtual ~Player() { delete[] name; }
};
```

**Златно правило:** ако клас има поне една виртуална функция (или ще се наследява), направете деструктора виртуален. Винаги.

### 1.6. Как работи това отвътре? Виртуални таблици (vtables)

За да разберете интуитивно защо динамичното свързване "работи", трябва да знаете как е реализирано:

1. За всеки клас с виртуални функции компилаторът създава **виртуална таблица (vtable)** — масив от указатели към реалните реализации на виртуалните функции на този клас.
2. Във всеки обект от такъв клас, в *началото* му, се поставя **скрит указател** към съответната vtable (наричан **vptr**).
3. При извикване `pp->print()`:
   - Компилаторът знае, че `print` е, да речем, 2-та виртуална функция в `Player`.
   - Генерира код, който отива на адреса, сочен от `pp`, чете vptr-а, отива в съответната vtable, взима указателя на позиция 2 и го извиква.

Това е защо динамичното свързване е малко по-бавно от статичното — допълнителна индирекция, но добавя само 1-2 такта.

```
Player обект:        vtable за Hero:
+---------------+   +---------------------+
| vptr ----------->| -> Hero::print()    |
| name           |   | -> Hero::attack()   |
| score          |   +---------------------+
+---------------+
```

### 1.7. Абстрактни методи и абстрактни класове

Понякога в основния клас няма смислена реализация на даден метод — той е просто *интерфейс*, който всеки наследник трябва да реализира по свой начин. За да укажем това, използваме **чиста виртуална функция**:

```cpp
class Shape {
public:
    virtual double area() const = 0;  // = 0 означава "чиста виртуална"
    virtual ~Shape() {}
};
```

Това казва на компилатора:
- Тази функция няма реализация в този клас.
- Класът е **абстрактен** — не можем да създаваме обекти от него.
- Всеки наследник, който иска да е "конкретен", трябва да я реализира.

```cpp
class Circle : public Shape {
    double radius;
public:
    Circle(double r) : radius(r) {}
    double area() const override { return 3.14159 * radius * radius; }
};

class Square : public Shape {
    double side;
public:
    Square(double s) : side(s) {}
    double area() const override { return side * side; }
};

Shape s;          // ГРЕШКА! Shape е абстрактен.
Circle c(5);      // OK
Shape* ps = &c;   // OK — указател към абстрактен клас е разрешен!
ps->area();       // OK — динамично свързване, извиква Circle::area()
```

**Особености на абстрактните класове:**
- Ако наследник не реализира някоя чиста виртуална функция, **той също остава абстрактен**.
- Абстрактните класове **могат** да имат конструктори и деструктори — извикват се косвено при създаване на наследник.
- Не могат да бъдат:
  - тип на член-данна (защото няма как да я инициализираме — не можем да създадем обект)
  - тип на връщан резултат по стойност (защото връщането по стойност означава копиране на обект)
  - тип на параметър по стойност (по същата причина)
- **Могат** да бъдат тип на указател или препратка.

**Интерфейс** е специален случай на абстрактен клас, който няма член-данни и всичките му член-функции са чисти виртуални.

### 1.8. Масиви от обекти и масиви от указатели към обекти

Тук стигаме до много важна особеност за подтиповия полиморфизъм. Имаме два различни случая:

#### Масив от обекти

```cpp
Player players[3];  // масив от 3 обекта от тип Player
```

Това заделя памет за **точно 3 обекта от тип `Player`**. Всеки от тях има фиксиран размер `sizeof(Player)`. **Не можем** да сложим тук `Hero` обект (който е по-голям) — наследник просто не се събира!

Дори да опитаме нещо подобно:

```cpp
Hero h("Гандалф", 100, 15);
players[0] = h;  // КОМПИЛИРА СЕ, НО Е ЛОШО!
```

Това се нарича **object slicing (нарязване на обект)** — частта `Hero` се "отрязва" и остава само `Player` информацията. Загубили сме данните и полиморфизмът не работи!

**Извод:** Масивите от обекти НЕ поддържат подтипов полиморфизъм. Те съдържат само обекти от точно посочения тип.

#### Масив от указатели към обекти

```cpp
Player* players[3];   // масив от 3 УКАЗАТЕЛЯ към Player
players[0] = new Hero("Гандалф", 100, 15);
players[1] = new Bot("R2D2", 50, "minimax", 0.8, 5);
players[2] = new Boss("Балрог", 200, 30, "aggressive", 0.9, 8, 50);
```

Сега всеки елемент е *указател*, който може да сочи към **Player или който и да е негов наследник**! Различните обекти могат да имат различни размери — те живеят в динамичната памет.

Когато извикваме виртуални методи през тези указатели, динамичното свързване работи прекрасно:

```cpp
for (int i = 0; i < 3; i++) {
    players[i]->print();  // всеки извиква СВОЯТА реализация!
}
```

**Не забравяйте да освободите паметта:**

```cpp
for (int i = 0; i < 3; i++) {
    delete players[i];  // изисква виртуален деструктор!
}
```

### 1.9. Пълен примерен код

Тук е цялостен работещ пример, който илюстрира всичко казано:

```cpp
#include <iostream>
#include <cstring>

// Помощна функция за копиране на C-низ в динамична памет
char* copyString(const char* s) {
    if (s == nullptr) return nullptr;
    size_t len = std::strlen(s);
    char* result = new char[len + 1];
    std::strcpy(result, s);
    return result;
}

// ====================== Базов клас Player ======================
class Player {
protected:
    char* name;
    int score;
public:
    Player(const char* n, int s) : score(s) {
        name = copyString(n);
    }

    // Конструктор за копиране — задължителен заради динамичната памет!
    Player(const Player& other) : score(other.score) {
        name = copyString(other.name);
    }

    // Операция за присвояване
    Player& operator=(const Player& other) {
        if (this != &other) {
            delete[] name;
            name = copyString(other.name);
            score = other.score;
        }
        return *this;
    }

    // ВИРТУАЛЕН деструктор — критично!
    virtual ~Player() {
        delete[] name;
    }

    // Виртуални методи — интерфейсът на Player
    virtual void print() const {
        std::cout << "Player " << name << " with score " << score << '\n';
    }

    virtual int getDamage() const {
        return 1;  // основна "щета"
    }

    const char* getName() const { return name; }
    int getScore() const { return score; }
};

// ====================== Производен клас Hero ======================
class Hero : public Player {
    int level;
public:
    Hero(const char* n, int s, int lvl) : Player(n, s), level(lvl) {}

    // Преопределяме виртуалните методи
    void print() const override {
        std::cout << "Hero " << name << " (level " << level
                  << ") with score " << score << '\n';
    }

    int getDamage() const override {
        return 5 + level * 2;
    }
};

// ====================== Абстрактен клас Shape ======================
class Shape {
public:
    virtual double area() const = 0;    // чиста виртуална
    virtual void print() const = 0;     // чиста виртуална
    virtual ~Shape() {}                 // виртуален деструктор
};

class Circle : public Shape {
    double radius;
public:
    Circle(double r) : radius(r) {}
    double area() const override {
        return 3.14159265 * radius * radius;
    }
    void print() const override {
        std::cout << "Circle (r=" << radius << ", area=" << area() << ")\n";
    }
};

class Rectangle : public Shape {
    double width, height;
public:
    Rectangle(double w, double h) : width(w), height(h) {}
    double area() const override {
        return width * height;
    }
    void print() const override {
        std::cout << "Rectangle (" << width << "x" << height
                  << ", area=" << area() << ")\n";
    }
};

// ====================== main: демонстрация ======================
int main() {
    // --- Демонстрация на статично vs динамично свързване ---
    Hero h("Гандалф", 100, 15);
    Player* pp = &h;
    pp->print();    // динамично → Hero::print()

    Player p2 = h;  // СРЯЗВАНЕ на обект! 
    p2.print();     // статично → Player::print() — губим Hero информацията

    // --- Масив от указатели (правилно за полиморфизъм) ---
    const int N = 3;
    Shape* shapes[N];
    shapes[0] = new Circle(5);
    shapes[1] = new Rectangle(3, 4);
    shapes[2] = new Circle(1);

    // Обработваме всички унифицирано
    double total = 0;
    for (int i = 0; i < N; i++) {
        shapes[i]->print();    // динамично свързване
        total += shapes[i]->area();
    }
    std::cout << "Total area: " << total << '\n';

    // Освобождаваме памет — благодарение на виртуалния деструктор
    // се извикват правилните деструктори
    for (int i = 0; i < N; i++) {
        delete shapes[i];
    }

    return 0;
}
```

### 1.10. Интуиция в общ план

Помислете за подтиповия полиморфизъм така: **една операция, много форми.**
- *Всички* играчи имат `print()`, но *всеки* играч се извежда различно.
- Кодът, който обработва играчите, не знае какъв точно тип са — само че имат `print()`.
- При промяна на изискванията просто добавяме нов наследник със собствена реализация. Стария код не се променя!

Това е сърцето на **Open/Closed принципа** в OOП: класовете трябва да са *отворени за разширение* (нови наследници) и *затворени за модификация* (стария код не се пипа).

## 2. Параметричен полиморфизъм. Шаблони на функции и на класове

### 2.1. Защо ни е?

Помислете си: написахте функция `swap`, която разменя две `int`-а:

```cpp
void swap(int& a, int& b) {
    int tmp = a;
    a = b;
    b = tmp;
}
```

Сега ви трябва за `double`. Копирате я и сменяте типа:

```cpp
void swap(double& a, double& b) {
    double tmp = a;
    a = b;
    b = tmp;
}
```

Сега за `char*`... и т.н. Виждате проблема: **една и съща логика, различни типове**. Хайде вместо това компилаторът сам да генерира версията за нас!

### 2.2. Шаблони на функции — синтаксис

```cpp
template <typename T>
void swap(T& a, T& b) {
    T tmp = a;
    a = b;
    b = tmp;
}
```

- `template <typename T>` — въвеждаме параметричен тип `T`.
- `T` може да участва в:
  - тялото на функцията (`T tmp = a;`)
  - типа на връщания резултат
  - типовете на параметрите

**Важно: шаблонът сам по себе си НЕ се компилира!** Той е *рецепта* за генериране на функции.

### 2.3. Как се използват шаблоните

```cpp
int a = 2, b = 3;
swap(a, b);           // компилаторът извежда T = int автоматично
swap<int>(a, b);      // явно указваме T = int

double x = 1.5, y = 2.5;
swap(x, y);           // компилаторът извежда T = double

char* p = "abc";
char* q = "xyz";
swap(p, q);           // T = char*
```

**Какво се случва зад кулисите:** при всяко използване с различен тип компилаторът *генерира нова функция*, която се компилира. Функция, генерирана от шаблон, се нарича **шаблонна функция** (template function).

### 2.4. Примерни шаблонни функции

#### Намиране на максимум:

```cpp
template <typename T>
T max(T a, T b) {
    return (a > b) ? a : b;
}

int main() {
    std::cout << max(3, 7) << '\n';         // 7
    std::cout << max(3.14, 2.71) << '\n';   // 3.14
    // std::cout << max(3, 7.0); // ГРЕШКА: нееднозначно — int или double за T?
    std::cout << max<double>(3, 7.0) << '\n'; // OK — явно указваме T = double
}
```

#### Обръщане на масив:

```cpp
template <typename T>
void reverse(T* arr, int size) {
    for (int i = 0; i < size / 2; i++) {
        T tmp = arr[i];
        arr[i] = arr[size - 1 - i];
        arr[size - 1 - i] = tmp;
    }
}

int main() {
    int a[8] = { 0, 1, 2, 3, 4, 5, 6, 7 };
    reverse(a, 8);  // T = int, изведено автоматично
    
    double d[4] = { 1.1, 2.2, 3.3, 4.4 };
    reverse(d, 4);  // T = double
}
```

### 2.5. Шаблони на класове

Същата идея, но за цели класове. Класически пример — динамичен масив:

```cpp
template <typename T>
class Array {
    T* data;
    int size;
    int capacity;
public:
    Array(int cap = 8) : size(0), capacity(cap) {
        data = new T[capacity];
    }

    // Конструктор за копиране — дълбоко копие
    Array(const Array& other) : size(other.size), capacity(other.capacity) {
        data = new T[capacity];
        for (int i = 0; i < size; i++) {
            data[i] = other.data[i];
        }
    }

    Array& operator=(const Array& other) {
        if (this != &other) {
            delete[] data;
            size = other.size;
            capacity = other.capacity;
            data = new T[capacity];
            for (int i = 0; i < size; i++) {
                data[i] = other.data[i];
            }
        }
        return *this;
    }

    ~Array() {
        delete[] data;
    }

    void push(const T& value) {
        if (size >= capacity) {
            // удвояваме капацитета
            capacity *= 2;
            T* newData = new T[capacity];
            for (int i = 0; i < size; i++) {
                newData[i] = data[i];
            }
            delete[] data;
            data = newData;
        }
        data[size++] = value;
    }

    T& operator[](int i) { return data[i]; }
    const T& operator[](int i) const { return data[i]; }
    int getSize() const { return size; }
};
```

**Терминология:**
- `template <typename T> class Array` — това е **шаблон на клас** (class template).
- `Array<int>` — това е **шаблонен клас** (template class) — конкретна инстанция на шаблона за `T = int`. Това е истински клас, който можем да използваме.

**Използване:**

```cpp
Array<int> a;       // a е от тип Array<int>
a.push(5);
a.push(10);

Array<double> d;    // d е друг клас!
d.push(3.14);

Array<int*> pointers; // масив от указатели — също работи
```

Internally компилаторът ще генерира два различни класа: един за `Array<int>` и един за `Array<double>`. Те не са свързани помежду си!

### 2.6. Член-функции на шаблонни класове, дефинирани извън класа

Това е малко по-сложен синтаксис. Ако искаме да дефинираме `push` извън класа:

```cpp
template <typename T>
void Array<T>::push(const T& value) {
    // ... реализация
}
```

Забележете:
- `template <typename T>` се повтаря преди дефиницията.
- `Array<T>::` (с типовия параметър) — а не само `Array::`.

### 2.7. Типови параметри по подразбиране

Можем да дадем стойност по подразбиране на типов параметър:

```cpp
template <typename T = int>
class Stack {
    // ...
};

Stack<> s1;        // T = int (по подразбиране)
Stack<double> s2;  // T = double
```

### 2.8. Параметри, които не са типове

Шаблоните могат да приемат и **стойностни параметри**, не само типове:

```cpp
template <typename T, int SIZE>
class FixedArray {
    T data[SIZE];
public:
    int getSize() const { return SIZE; }
    T& operator[](int i) { return data[i]; }
};

FixedArray<int, 10> a;   // масив от 10 int-а
FixedArray<double, 5> b; // масив от 5 double-а
```

### 2.9. Кога шаблоните се компилират?

Шаблон се компилира **само когато се инстанцира** (т.е. когато се използва с конкретни типове). Затова обикновено целият код на шаблоните се пише в `.h` файлове, а не в `.cpp`.

Това има интересно следствие: ако дадена операция върху `T` не съществува, грешката идва чак при използването:

```cpp
template <typename T>
T sum(T a, T b) {
    return a + b;  // изисква T да поддържа operator+
}

struct Bad {};
Bad x, y;
// sum(x, y);  // ГРЕШКА при компилация, но шаблонът сам по себе си се компилира OK
sum(1, 2);     // OK
```

### 2.10. Сравнение: параметричен vs подтипов полиморфизъм

| Аспект | Параметричен (шаблони) | Подтипов (виртуални) |
|--------|------------------------|----------------------|
| Кога се избира типът | компилация | изпълнение |
| Производителност | същата като ръчно писан код | малка цена за vtable |
| Размер на изпълнимия файл | расте с всяка инстанциация | не |
| Изисква наследяване | НЕ | ДА |
| Изисква обща сигнатура | НЕ (просто типът трябва да поддържа операциите) | ДА (унаследен абстрактен/виртуален метод) |
| Грешките се ловят на | компилация | изпълнение (рядко, обикновено просто `null`) |

**Кога кое използваме?**

- **Шаблони**: когато имаме *един и същ алгоритъм* за множество несвързани типове (контейнери, sort, swap, max...).
- **Виртуални функции**: когато имаме *йерархия от свързани типове*, които споделят интерфейс, но всеки реализира по различен начин.

### 2.11. Шаблони и наследяване — могат да се комбинират

Това е напреднало, но интересно:

```cpp
// Клас, наследяващ шаблонен клас:
class IntMatrix : public Array<int> { /* ... */ };

// Шаблон, наследяващ обикновен клас:
template <typename T>
class Matrix : public IntArray { /* ... */ };

// Шаблон, наследяващ шаблонен клас (фиксирана инстанция):
template <typename T>
class Matrix : public Array<void*> { /* ... */ };

// Шаблон, наследяващ шаблон (параметрична инстанция):
template <typename T>
class Matrix : public Array<Array<T>> { /* ... */ };
```

## 3. Множествено наследяване

### 3.1. Какво е?

В C++ е разрешено един клас да има **повече от един основен клас**:

```cpp
class Hero : public Player { /* ... */ };
class Bot : public Player, public AI { /* ... */ };  // ДВА основни класа
```

**Идеята:** `Bot` е едновременно `Player` (играч в играта) И `AI` (изкуствен интелект). Той наследява компоненти от двата.

Синтаксис:

```cpp
class <име> : [<видимост>] <базов_клас>
              {, [<видимост>] <базов_клас>}
{ <тяло> };
```

Където `<видимост>` е `public`, `protected` или `private`.

### 3.2. Примерна йерархия

Нека разгледаме характерна йерархия от компютърна игра:

```cpp
class Player {
protected:
    char* name;
    int score;
public:
    Player(const char* n, int s);
    virtual ~Player();
    virtual void print() const;
    const char* getName() const;
};

class Hero : public Player {
    int level;
public:
    Hero(const char* n, int s, int lvl);
    void print() const override;
};

class AI {
protected:
    char* algorithm;
    double threshold;
    int difficulty;
public:
    AI(const char* alg, double thr, int diff);
    virtual ~AI();
    virtual void think() const;
};

class Bot : public Player, public AI {
public:
    Bot(const char* n, int s, const char* alg, double thr, int diff)
        : Player(n, s), AI(alg, thr, diff) {}
    void print() const override {
        // Имаме достъп и до Player::name, и до AI::algorithm!
    }
};
```

### 3.3. Проблем 1: Косвено повторно наследяване — "Deadly Diamond of Death"

Сега да усложним нещата. Имаме `Boss`, който е *по-силна* версия на `Bot`, но и *по-силна* версия на `Hero` (играч с високо ниво):

```cpp
class Boss : public Hero, public Bot {
    int damage;
public:
    // ...
};
```

Получава се **диамантна йерархия**:

```
        Player                              Player    AI
         /  \                                 \   |   /
       Hero  Bot         което в C++ е →       Hero  Bot
         \  /                                    \  /
         Boss                                    Boss
```

`Boss` наследява `Player` **два пъти** — веднъж през `Hero`, веднъж през `Bot`!

**Физическо представяне на диаманта в паметта** (без виртуално наследяване):

```
Boss обект:
+----------------+----------------+----------------+
| Hero част      | Bot част       | Boss част      |
| +------------+ | +------------+ |                |
| | Player    | | | Player    | | | damage         |
| | name      | | | name      | | |                |
| | score     | | | score     | | |                |
| +------------+ | +------------+ |                |
| | level     | | | algorithm  | |                |
| |           | | | threshold  | |                |
| |           | | | difficulty | |                |
| +------------+ | +------------+ |                |
+----------------+----------------+----------------+
```

`name` и `score` се **повтарят**! Това поражда множество проблеми:

1. **Излишна памет** — две копия на едно и също.
2. **Нееднозначност при достъп**:
   ```cpp
   Boss b("Балрог", 100, ...);
   b.getName();  // ГРЕШКА! Кое name? Hero::name или Bot::name?
   ```
3. **Нееднозначност при преобразуване**:
   ```cpp
   Boss b;
   Player* pp = &b;  // ГРЕШКА! Кой Player подобект?
   ```
4. **"Раздвояване на личността"** — Boss концептуално е *един* играч, но физически има *две* играчески идентичности.

Можем да решим проблема с явно указване:

```cpp
Boss b("Балрог", 100, ...);
b.Hero::getName();   // достъп през Hero
b.Bot::getName();    // достъп през Bot
Player* pp = (Hero*)&b;  // явно преобразуване
```

Но това е грозно и порочно.

### 3.4. Решение: Виртуално наследяване

C++ ни позволява да укажем, че даден основен клас трябва да е **споделен** между наследниците. Това става с ключовата дума `virtual` при наследяване:

```cpp
class Hero : virtual public Player { /* ... */ };
class Bot : virtual public Player, public AI { /* ... */ };
class Boss : public Hero, public Bot { /* ... */ };
```

**Важно: един клас не може да е "виртуален" сам по себе си.** Виртуалността е свойство на връзката *наследяване*, а не на класа. Казваме "Player е виртуален основен клас за Hero" — т.е. наследяването е виртуално.

**Какво се случва сега?**

```
Boss обект:
+--------+--------+-------------------+--------+--------+
| Hero   | Bot               | Boss  | Player (споделен)|
|        |   AI              |       |                  |
| level  | algo, thr, diff   | damage| name, score      |
+--------+-------------------+-------+------------------+
```

Има **само едно копие** на `Player` подобект, споделено между `Hero` и `Bot`. Решихме всички проблеми наведнъж!

### 3.5. Конструктори на виртуални основни класове

С виртуалното наследяване идва нова сложност. Кой извиква конструктора на `Player`?

Без виртуално наследяване — `Hero` го извиква, а `Bot` го извиква (всеки за своя си `Player` подобект). Имаме *два* извика на конструктор на `Player`.

С виртуално наследяване — има само **един** `Player` подобект, така че конструкторът му трябва да се извика *точно веднъж*. Кой го прави?

**Отговорът:** Най-производният клас (т.е. `Boss`) е отговорен за инициализацията на виртуалния базов клас.

```cpp
class Boss : public Hero, public Bot {
    int damage;
public:
    Boss(const char* _name, int _s, int _lvl,
         const char* _algo, double _threshold,
         int _difficulty, int _damage)
        : Player(_name, _s),   // ← Boss инициализира Player директно!
          Hero(_name, _s, _lvl),
          Bot(_name, _s, _algo, _threshold, _difficulty),
          damage(_damage)
    {}
};
```

**Важно:**
- Извикването `Hero(_name, _s, _lvl)` от `Boss`-конструктора **не** извиква конструктора на `Player` — той вече е извикан от `Boss`.
- Ако `Boss` не инициализира `Player` изрично, ще се извика конструкторът по подразбиране на `Player` — ако такъв няма, ще има грешка при компилация.

### 3.6. Ред на конструкторите

При множествено наследяване редът на извикване е:

1. Всички виртуални основни класове (по реда на дълбочинно обхождане).
2. Всички невиртуални основни класове (по реда, в който са изброени в декларацията).
3. Обектите-членове (по реда, в който са декларирани).
4. Тялото на собствения конструктор.

Деструкторите се извикват в *обратен* ред.

### 3.7. Кога използваме видимост `public`/`protected`/`private` при наследяване?

| Достъп в базовия клас | При public наследяване | При protected наследяване | При private наследяване |
|----------------------|------------------------|--------------------------|-------------------------|
| public               | public                 | protected                | private                 |
| protected            | protected              | protected                | private                 |
| private              | недостъпен             | недостъпен               | недостъпен              |

- **`public` наследяване** — "Е" (is-a). `Hero` Е `Player`. Това е истинско подтипиране.
- **`protected` наследяване** — "семейно" използване. Само наследниците могат да третират класа като базов.
- **`private` наследяване** — "егоистично" използване. Външно никой не знае, че има наследяване. Това всъщност е по-близо до композиция.

По подразбиране (ако не сме указали) видимостта е `private` при `class` и `public` при `struct`.

### 3.8. Кога е полезно множествено наследяване и кога не?

**Полезно когато:**
- Реализираме няколко интерфейса (абстрактни класове). Това е "безопасно" множествено наследяване, защото няма данни, които да се повторят.
- Истински имаме клас, който е концептуално няколко неща наведнъж.

**Опасно когато:**
- Има данни и в двата базови класа — диамантният проблем винаги е там.
- Базовите класове имат методи с еднакви имена — нееднозначност.

В много съвременни езици (Java, C#) множественото наследяване на класове е напълно забранено — позволено е само за интерфейси. C++ е по-либерален, но с цената на сложността.

### 3.9. Пълен примерен код

```cpp
#include <iostream>
#include <cstring>

char* copyString(const char* s) {
    if (s == nullptr) return nullptr;
    size_t len = std::strlen(s);
    char* result = new char[len + 1];
    std::strcpy(result, s);
    return result;
}

// ====================== Player (виртуален базов клас) ======================
class Player {
protected:
    char* name;
    int score;
public:
    Player(const char* n, int s) : score(s) {
        name = copyString(n);
        std::cout << "Player(" << n << ") constructed\n";
    }
    virtual ~Player() {
        std::cout << "~Player(" << name << ")\n";
        delete[] name;
    }
    virtual void print() const {
        std::cout << "Player: " << name << " score=" << score;
    }
    const char* getName() const { return name; }
};

// ====================== Hero — наследява Player ВИРТУАЛНО ===================
class Hero : virtual public Player {
protected:
    int level;
public:
    Hero(const char* n, int s, int lvl) : Player(n, s), level(lvl) {
        std::cout << "Hero constructed (lvl=" << lvl << ")\n";
    }
    ~Hero() override {
        std::cout << "~Hero()\n";
    }
    void print() const override {
        Player::print();
        std::cout << " level=" << level;
    }
};

// ====================== AI — самостоятелен клас (не наследява Player) =======
class AI {
protected:
    char* algorithm;
    double threshold;
public:
    AI(const char* alg, double thr) : threshold(thr) {
        algorithm = copyString(alg);
        std::cout << "AI(" << alg << ") constructed\n";
    }
    virtual ~AI() {
        std::cout << "~AI(" << algorithm << ")\n";
        delete[] algorithm;
    }
    virtual void think() const {
        std::cout << "Thinking with " << algorithm
                  << " (threshold=" << threshold << ")";
    }
};

// ====================== Bot — наследява Player ВИРТУАЛНО + AI ===============
class Bot : virtual public Player, public AI {
public:
    Bot(const char* n, int s, const char* alg, double thr)
        : Player(n, s), AI(alg, thr) {
        std::cout << "Bot constructed\n";
    }
    ~Bot() override {
        std::cout << "~Bot()\n";
    }
    void print() const override {
        Player::print();
        std::cout << " [Bot with ";
        think();
        std::cout << "]";
    }
};

// ====================== Boss — диамантна йерархия =========================
class Boss : public Hero, public Bot {
    int damage;
public:
    // ВАЖНО: Boss трябва ДИРЕКТНО да инициализира Player,
    // защото Player е виртуален базов клас.
    Boss(const char* n, int s, int lvl,
         const char* alg, double thr, int dmg)
        : Player(n, s),               // ← директна инициализация на виртуалния базов клас
          Hero(n, s, lvl),
          Bot(n, s, alg, thr),
          damage(dmg)
    {
        std::cout << "Boss constructed (damage=" << dmg << ")\n";
    }

    ~Boss() override {
        std::cout << "~Boss()\n";
    }

    void print() const override {
        Player::print();
        std::cout << " level=" << level
                  << " damage=" << damage
                  << " (Boss with ";
        think();
        std::cout << ")";
    }
};

// ====================== main ===============================================
int main() {
    std::cout << "=== Construction ===\n";
    Boss b("Балрог", 1000, 50, "aggressive", 0.95, 75);

    std::cout << "\n=== Usage ===\n";
    b.print();
    std::cout << '\n';

    // НЯМА нееднозначност — има само едно Player копие!
    std::cout << "Name: " << b.getName() << '\n';

    // Преобразуването също е еднозначно
    Player* pp = &b;
    pp->print();    // динамично свързване → Boss::print()
    std::cout << '\n';

    std::cout << "\n=== Destruction ===\n";
    return 0;
    // При излизане от main: Boss → Bot → Hero → AI → Player
}
```

**Типичен изход:**

```
=== Construction ===
Player(Балрог) constructed       ← конструктор на виртуалния базов клас (само веднъж!)
Hero constructed (lvl=50)
AI(aggressive) constructed
Bot constructed
Boss constructed (damage=75)

=== Usage ===
Player: Балрог score=1000 level=50 damage=75 (Boss with Thinking with aggressive (threshold=0.95))
Name: Балрог
Player: Балрог score=1000 level=50 damage=75 (Boss with Thinking with aggressive (threshold=0.95))

=== Destruction ===
~Boss()
~Bot()
~AI(aggressive)
~Hero()
~Player(Балрог)
```

### 3.10. Интуиция

- **Множественото наследяване е мощно, но опасно.** Използвайте го, когато наистина имате нужда.
- **Диамантният проблем е реален.** Винаги мислете за виртуално наследяване, когато имате обща "прародина".
- **Виртуалното наследяване има цена** — реализира се чрез vtable указатели, които увеличават размера на обектите и забавят достъпа.
- **Конструкторът на виртуалния базов клас се извиква от най-производния клас.** Не от междинните.
- **Често по-добро решение е композиция** — `Bot` може *да съдържа* `AI` обект, вместо да го наследява. Това е същата идея ("Бот ИМА AI", не "Бот Е AI"), но без диамантни кошмари.

## 4. Резюме на ключовите идеи

### Подтипов полиморфизъм (виртуални функции)
- `virtual` → динамично свързване → правилният метод се избира по време на изпълнение.
- Динамично свързване само през указател/препратка, не през обект.
- Чисти виртуални (`= 0`) → абстрактен клас → не може да създаваме обекти.
- Виртуален деструктор е задължителен, когато ще имаме `delete` през указател на базов клас.
- Масиви: за полиморфизъм — масив от *указатели*, не от обекти.
- Object slicing — копиране на наследник в обект на базов клас "отрязва" допълнителната информация.

### Параметричен полиморфизъм (шаблони)
- `template <typename T>` — за един код, който работи с много типове.
- Компилаторът генерира конкретна функция/клас за всеки използван тип.
- Грешките идват при инстанциация, не при дефиниция на шаблона.
- Цялата дефиниция обикновено е в header файлове.

### Множествено наследяване
- C++ позволява няколко основни класове.
- Косвено повторно наследяване → диамантен проблем.
- Решение: `virtual` наследяване → споделен подобект.
- Конструкторът на виртуалния базов клас се извиква от най-производния клас.
- Често по-добра алтернатива — композиция или интерфейси (абстрактни класове без данни).

## 5. Често задавани въпроси на изпит

**Въпрос:** Защо конструкторите не могат да бъдат виртуални?  
**Отговор:** Защото в момента на извикване на конструктор обектът още не е напълно конструиран. vtable указателят се настройва *по време на* конструктора, така че няма как да се избере "правилната" версия преди да знаем типа. Самият избор на тип се извършва "отвън" — при изричното `new T(...)`.

**Въпрос:** Защо виртуалната функция, извикана от конструктора, се свързва статично?  
**Отговор:** Когато `Player::Player()` се изпълнява, виртуалната таблица на обекта още сочи към таблицата на `Player`, не на наследника. Това е защото частта на наследника още не е инициализирана и не би било безопасно да се вика негов метод.

**Въпрос:** Защо `Boss` инициализира `Player` директно, въпреки че `Player` се наследява от `Hero` и `Bot`, а не от `Boss`?  
**Отговор:** При виртуално наследяване има само *един* `Player` подобект, споделен. Той трябва да се инициализира точно веднъж и това е отговорност на най-производния клас (`Boss`). Извикването `Hero(...)` от `Boss`-конструктора не извиква `Player`'s конструктор, защото `Player` вече е инициализиран.

**Въпрос:** Какъв е размерът на обекти с виртуални функции в сравнение с такива без?  
**Отговор:** Обикновено повече с размера на един указател (vptr). Например, ако `Player` без виртуални функции е 16 байта, с виртуални става 24 байта на 64-битова система.

**Въпрос:** Защо не можем да имаме виртуални шаблонни член-функции?  
**Отговор:** Защото броят на инстанциациите на шаблона не е известен предварително — нов код може да го инстанцира по-късно. Виртуалната таблица обаче има фиксиран размер, определен при компилация. Тези два механизма са фундаментално несъвместими.

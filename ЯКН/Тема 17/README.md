# Обектно-ориентирано програмиране — Въпроси 1 и 2 от ДИ

## 0. Преглед на принципите на ООП

ООП стъпва на четири стълба. Полезно е първо да си изградиш интуиция за тях, защото целият останал материал ги конкретизира.

**Абстракция.** Гледаме на даден тип данни през призмата на *какво* прави, а не *как* е реализиран. Когато ползваш `Stack`, не те интересува дали вътре е масив или свързан списък — интересува те само, че имаш `push` и `pop`.

**Капсулация.** Скриваме реализацията зад интерфейс. Полетата са `private`, операциите — `public`. Така, ако променим вътрешното представяне, потребителите на класа не усещат.

**Наследяване.** Изграждаме нови класове чрез разширяване на стари. Връзка от тип "е" (is-a): всеки `Hero` *е* `Player`.

**Полиморфизъм.** Един и същ интерфейс работи върху различни типове. (Подробно е обект на следващите въпроси — тук го споменаваме само за пълнота.)

Тези принципи не са независими — те се поддържат един друг. Капсулацията позволява абстракция; наследяването използва капсулация (на наследения клас); полиморфизмът се крепи на наследяването.

# Въпрос 1

## 1.1 От структури към класове — абстракция

### От къде започваме?

В езика C имаме `struct` — групираш няколко полета под едно име:

```cpp
struct Rational {
    int numerator;
    int denominator;
};
```

После пишеш отделни функции, които работят със структурата:

```cpp
Rational add(Rational a, Rational b);
void print(Rational r);
```

Проблем: **нищо не пречи на потребителя да пипа полетата директно.** Може да напише `r.denominator = 0;` и да счупи инварианта (знаменателят винаги да е различен от 0). Освен това *всеки* код, който знае как е представено рационалното число, ще трябва да се преписва, ако променим представянето (напр. ако решим да пазим числителя и знаменателя винаги съкратени).

### Идея за абстракция

Искаме да изолираме **вътрешното представяне** на типа от **операциите** над него. Това означава:

1. Полетата (физическото представяне) ги обявяваме за достъпни само вътре в типа.
2. Външният свят работи с типа само през публичен интерфейс — селектори (геттери), мутатори (сетери) и операции.

Така **външните функции "не знаят" как е представен обектът**, те работят само през операциите. Ако променим представянето, те остават непокътнати.

### Класът — реализация на тази идея

В C++ имаме `class` точно за това. Технически `class` и `struct` са почти едно и също — единствената разлика е, че **в `struct` всичко е `public` по подразбиране, а в `class` всичко е `private` по подразбиране**. Затова идиоматично се ползва `class`, когато искаме капсулация.

```cpp
class Rational {
    int num;   // числител — private по подразбиране
    int den;   // знаменател

public:
    Rational(int n, int d);
    int getNumerator() const;
    int getDenominator() const;
};
```

Сега `r.num = 5;` отвън е грешка по време на компилация. Външният код може само да извика конструктора и геттерите.

> **Интуиция:** Класът обединява *данни* + *операции над тях* в един и същ "пакет". Полетата са вътрешни (никой отвън не може да ги пипа произволно), методите образуват външния интерфейс.

## 1.2 Декларация на клас и декларация на обект

### Деклариране на клас

Синтаксисът е:

```cpp
class <име-на-клас> {
    <спецификатор-за-достъп>:
        <член-данни>
        <член-функции>
    <спецификатор-за-достъп>:
        ...
};   // НЕ забравяй точката и запетаята!
```

Спецификаторите за достъп са `private`, `protected` и `public`. Те могат да се срещат многократно и важат до следващия спецификатор.

#### Особености

- **Конструкторите и деструкторите нямат тип** (нито `void`, нито нещо друго). Името на конструктора съвпада с името на класа; името на деструктора е `~<име-на-клас>`.
- **Деструкторът няма параметри.**
- **Директна рекурсия в член-данните е забранена** — клас не може да има поле от своя собствен тип:

```cpp
class Employee {
    Employee boss;   // ГРЕШКА! Безкрайно вложени обекти.
};
```

  Но **индиректна рекурсия чрез указател** е напълно разрешена:

```cpp
class Employee {
    Employee* boss;   // ОК — само указател към обект от същия клас.
};
```

  Това е често срещано при свързани структури от данни.

- Член-функциите могат да връщат стойност от всякакъв тип, включително и от **същия клас**.

### Пълен пример — клас `Player` без `std::string`

> Курсът избягва `std::string` от ООП, защото идеята е да управляваш паметта сам. Затова ползваме `char*` и динамична памет за низове.

```cpp
#include <cstring>   // за strlen, strcpy
#include <iostream>

class Player {
    char* name;   // динамичен низ — собственост на обекта
    int   score;

public:
    // Конструктори, деструктор — ще ги обсъдим в детайли по-долу
    Player(char const* n, int s);
    Player(Player const& other);
    Player& operator=(Player const& other);
    ~Player();

    // Селектори (за четене)
    char const* getName()  const;
    int         getScore() const;

    // Мутатори (за запис)
    void setName(char const* n);
    void setScore(int s);

    // Други операции
    void print() const;
};
```

### Деклариране на обект

След като класът е дефиниран, можем да създаваме обекти. Обектите могат да живеят на три места:

#### 1) На програмния стек (автоматични обекти)

```cpp
Player p1("Asen", 100);   // вика конструктор с (char const*, int)
Player p2;                // вика конструктор по подразбиране (ако има такъв)
```

Тези обекти **се унищожават автоматично**, когато излязат от обхвата си — компилаторът извиква деструктора им.

#### 2) В статичната памет (глобални/статични обекти)

```cpp
static Player champion("Bot", 9999);
```

Живеят, докато живее програмата.

#### 3) В динамичната памет (с `new`)

Три варианта:

```cpp
Player* p = new Player;             // конструктор по подразбиране
Player* q = new Player("Ivan", 50); // конструктор с параметри
Player* arr = new Player[10];       // масив — за всеки елемент конструктор по подразбиране
```

**Внимание:** обекти, създадени с `new`, **не се унищожават автоматично**. Трябва да извикаш `delete p;` (или `delete[] arr;` за масив). Иначе има изтичане на памет.

> **Интуиция:** Между декларация (class) и инстанция (object) е същата разлика като между *чертеж на сграда* и *самата сграда*. Класът описва типа; обектът е конкретен екземпляр.

## 1.3 Методи

### Какво е метод?

Метод е функция, която принадлежи на клас. Декларира се **вътре** в тялото на класа, а може да се **дефинира** както вътре, така и вън (с оператора за указване на област `::`).

```cpp
class Rational {
    int num, den;
public:
    // Декларация вътре
    void print() const;
    
    // Дефиниция вътре — става автоматично inline
    int getNumerator() const { return num; }
};

// Дефиниция вън (по-чисто за по-сложни методи)
void Rational::print() const {
    std::cout << num << '/' << den;
}
```

### Скритият параметър `this`

Всеки **нестатичен** метод получава скрит параметър `this` — указател към обекта, върху който е извикан методът.

```cpp
class Counter {
    int value;
public:
    void increment() {
        // this е тип Counter*
        this->value++;   // явно
        value++;         // същото — this-> се подразбира
    }
};
```

Когато пишеш `value` без `this->`, компилаторът добавя `this->` сам. Това понякога е удобно — но трябва да знаеш, че го има.

### `const` методи

Метод, който **не променя** обекта, трябва да се обяви като `const`:

```cpp
int  getScore() const;   // не променя обекта
void setScore(int s);    // променя обекта — НЕ е const
```

`const` се пише след списъка с параметри, преди тялото. Технически той променя типа на `this` от `Player*` на `Player const*`. Това означава:

- В тялото на `const` метод **не можеш да променяш член-данните**.
- В тялото на `const` метод **можеш да викаш само други `const` методи**.

Защо това е важно? Защото върху `const` обект (например параметър `Player const& p`) можеш да викаш **само `const` методи**. Ако `getName()` не беше `const`, нямаше да можеш да я викаш върху `const` Player.

**Практическо правило:** *Всеки селектор задължително е `const`. Всеки мутатор не е `const`.*

### Предаване на параметри

Имаме няколко начина:

```cpp
void f1(Player p);          // 1) по стойност — копира обекта (бавно за тежки обекти!)
void f2(Player& p);         // 2) по препратка — може да го промени
void f3(Player const& p);   // 3) по константна препратка — НЕ може да го промени (ефективно!)
void f4(Player* p);         // 4) по указател — може да е nullptr
void f5(Player const* p);   // 5) по указател към const
```

**Кога кое?**

- **`T`** (по стойност) — за вградени типове (`int`, `double`, `char`) и за малки леки обекти. За тежки класове е скъпо, защото вика конструктор за копиране.
- **`T const&`** (константна препратка) — **най-използваното за тежки обекти**, които не променяме. Бързо (без копиране) и безопасно.
- **`T&`** (препратка) — когато искаме да *променим* подадения обект (типичен мутатор-параметър).
- **`T*`** (указател) — когато стойността може да липсва (`nullptr`) или когато преместваме собственост.

**Връщане на резултат — аналогично:**

```cpp
Player        copy();        // връща копие — вика конструктор за копиране
Player&       reference();   // връща препратка — внимавай да НЕ е към локален обект!
Player const& constRef();
Player*       pointer();
```

> ⚠️ Никога не връщай препратка или указател към локален обект на функцията — той ще е унищожен, когато функцията приключи. Освен ако обектът е статичен или е в динамичната памет.

### Селектори и мутатори — типов шаблон

```cpp
class Player {
    char* name;
    int   score;
public:
    // Селектори: const, връщат стойност или const&
    char const* getName()  const { return name;  }
    int         getScore() const { return score; }

    // Мутатори: не са const, нямат връщана стойност (или връщат *this)
    void setScore(int s) { score = s; }
};
```

## 1.4 Основни видове конструктори

### Какво е конструктор?

Конструкторът е специален метод, който:

- се вика автоматично при създаване на обект;
- инициализира паметта на обекта;
- гарантира, че **преди да започне работата с обекта, той е във валидно състояние**;
- позволява предварително задаване на стойности на полетата.

**Особености:**
- Името му съвпада с името на класа.
- Няма тип на връщана стойност (дори не `void`).
- Може да е претоварен (повече от един конструктор с различни параметри).

### Видове конструктори

#### а) Конструктор по подразбиране (default constructor)

Конструктор **без параметри** (или такъв, при който всички параметри имат стойности по подразбиране).

```cpp
class Player {
    char* name;
    int   score;
public:
    Player() {
        name  = new char[1];
        name[0] = '\0';   // празен низ
        score = 0;
    }
};
```

Извиква се при:
- `Player p;` (без аргументи);
- `Player arr[5];` (масив на стека);
- `new Player[5]` (масив в динамичната памет);
- когато обект от тип `Player` е поле в друг клас и не е инициализиран изрично.

**Ако не дефинираш нито един конструктор**, компилаторът генерира конструктор по подразбиране автоматично (системен). Той просто извиква конструкторите по подразбиране на всички член-данни (полетата от вграден тип остават неинициализирани!).

**Ако дефинираш *поне един* конструктор с параметри, но не дефинираш конструктор по подразбиране**, то компилаторът *не* генерира такъв. Тогава `Player p;` ще е грешка.

#### б) Конструктор с параметри

Приема една или повече стойности за инициализация.

```cpp
Player::Player(char const* n, int s) {
    name = new char[strlen(n) + 1];
    strcpy(name, n);
    score = s;
}
```

Викане:

```cpp
Player p("Asen", 100);
Player* q = new Player("Ivan", 50);
```

#### в) Конструктор за копиране (copy constructor)

Специален конструктор с точно един параметър — **константна препратка към същия клас**:

```cpp
Player::Player(Player const& other) {
    score = other.score;
    name  = new char[strlen(other.name) + 1];
    strcpy(name, other.name);
}
```

Извиква се при:
- инициализация на обект с друг обект: `Player p2(p1);` или `Player p2 = p1;` (внимание: това *не* е присвояване, а инициализация!);
- предаване на параметър по стойност;
- връщане на резултат по стойност.

**Защо параметърът е `Player const&`?**
- *Защо препратка?* Ако беше по стойност, при викане на конструктора за копиране ще се извика... конструкторът за копиране → безкрайна рекурсия.
- *Защо `const`?* За да можем да копираме и от `const` обекти, и да гарантираме, че оригиналът не се променя.

Ако не пишем свой конструктор за копиране, компилаторът генерира **системен**, който прави *плитко копие* (member-wise copy) — копира всяко поле "сляпо". За полета-обекти вика техните копиращи конструктори; за полета от вграден тип просто копира байтовете.

**Важно:** при работа с динамична памет системният конструктор НЕ работи коректно, защото копира само указателя — двата обекта започват да сочат към една и съща памет (виж раздел [1.6](#16-raii-и-голямата-четворка)).

#### г) Конструктор за преобразуване на тип

Това е **конструктор с точно един параметър**, който може да служи и за неявно преобразуване на типове.

```cpp
class Rational {
    int num, den;
public:
    Rational(int n) : num(n), den(1) {}   // int → Rational
};

void f(Rational r);

f(5);   // 5 неявно се преобразува до Rational(5), т.е. 5/1
```

Ако не искаме това неявно преобразуване, слагаме ключовата дума `explicit`:

```cpp
explicit Rational(int n);   // тогава f(5) е грешка, трябва f(Rational(5))
```

### Инициализиращ списък

Това е **изключително важна** конструкция. Синтаксисът е:

```cpp
<име-на-клас>::<име-на-клас>(<параметри>)
    : <член-данна-1>(<израз-1>),
      <член-данна-2>(<израз-2>),
      ...
{
    // тяло
}
```

Пример:

```cpp
class Rational {
    int num, den;
public:
    Rational(int n, int d) : num(n), den(d) { }
};
```

**Защо инициализиращ списък, а не присвояване в тялото?**

```cpp
// Вариант А — с инициализиращ списък (добре)
Rational(int n, int d) : num(n), den(d) { }

// Вариант Б — с присвояване в тялото (по-зле)
Rational(int n, int d) {
    num = n;
    den = d;
}
```

При вариант Б полетата `num` и `den` **първо се инициализират** (с конструктор по подразбиране) и **после се присвояват**. Това са две операции вместо една.

Освен това има случаи, в които **задължително** се ползва инициализиращ списък:
- инициализация на `const` поле;
- инициализация на поле от тип препратка (`int&`);
- инициализация на поле от тип, който няма конструктор по подразбиране;
- викане на конструктор на базов клас (при наследяване — виж въпрос 2).

**Правило за интуиция:** *Винаги, когато можеш, използвай инициализиращ списък.*

### Жизнен цикъл на обект — кратко

1. Заделя се памет (на стека или с `new`).
2. Извиква се конструктор.
3. Работим с обекта.
4. Достига се краят на областта на действие (или се вика `delete`).
5. Извиква се деструктор.
6. Освобождава се паметта.

## 1.5 Деструктор

Деструкторът е специален метод, който се вика **автоматично** в момента, в който обектът се унищожава.

```cpp
class Player {
    char* name;
public:
    Player(char const* n);
    ~Player();   // деструктор — име = ~<име-на-клас>
};

Player::~Player() {
    delete[] name;   // освобождаваме динамично заделената памет
}
```

**Особености:**
- Има точно **един** деструктор на клас.
- **Няма параметри** и **няма тип на връщана стойност**.
- Не може да се претоварва.
- Извиква се автоматично при:
  - край на областта на действие (за автоматичен обект);
  - `delete` (за обект в динамичната памет);
  - `delete[]` (за масив — вика се за всеки елемент);
  - край на програмата (за статични/глобални обекти).

**За какво ни е?** За да освобождава ресурси, които обектът държи: динамична памет, файлови дескриптори, мрежови връзки, заключвания и пр. С други думи, деструкторът е "обратното" на конструктора по отношение на ресурсите.

> **Интуиция:** *Който заделя, той освобождава.* Ако в конструктора има `new`, в деструктора трябва да има `delete` или `delete[]`.

## 1.6 RAII и Голямата четворка

### Какво е RAII?

**RAII** = *Resource Acquisition Is Initialization* — "придобиването на ресурс е инициализация". 

Това е една от най-важните идеи в C++. Същината й е: **обектът придобива ресурс в конструктора си и го освобождава в деструктора си**. Така, докато обектът е "жив", ресурсът е валиден, а в момента, в който обектът умре, ресурсът автоматично се освобождава.

**Защо това е страхотно?**
- Не забравяш да освободиш ресурс — компилаторът се грижи за това.
- Дори ако възникне изключение, деструкторът пак ще се извика → ресурсът се освобождава.
- Логиката на работа с ресурси е концентрирана на едно място (в класа), а не разпръсната из целия код.

**Пример:** клас, който държи динамичен масив.

```cpp
class IntArray {
    int* data;
    int  size;
public:
    IntArray(int n)
        : data(new int[n]), size(n) { }   // придобиваме ресурс
    
    ~IntArray() {
        delete[] data;                    // освобождаваме го
    }
    
    int& operator[](int i) { return data[i]; }
};

void f() {
    IntArray arr(100);
    arr[0] = 42;
    // ...
}   // тук arr излиза от обхват → вика се ~IntArray → паметта се освобождава
```

Не пишеш нито един `delete[]` извън класа. Всичко се случва "от само себе си".

### Стратегии за управление на ресурс (от лекциите)

**Стратегия "собственост":** точно един обект (един указател-собственик) държи ресурса. Други указатели може да го "ползват", но не могат да го освобождават. Освобождаването става **през собственика**, обикновено в неговия деструктор.

Това е базовата идея зад RAII: собственикът е поле на обект, паметта се освобождава от деструктора, а докато обектът е жив — паметта е валидна.

### Голямата четворка

Когато обектът управлява ресурс (най-често: динамична памет), системно генерираните функции **не работят коректно**. Затова трябва да дефинираме **четири** функции, наричани **Голямата четворка** *(Big Four)*:

| Член-функция                  | Сигнатура                                    | Кога се вика                                                          |
|-------------------------------|----------------------------------------------|-----------------------------------------------------------------------|
| Конструктор по подразбиране   | `T()`                                        | Инициализация без аргументи; масиви в динамична памет.                |
| Конструктор за копиране       | `T(T const& other)`                          | `T b(a);`, предаване по стойност, връщане по стойност.                |
| Операция за присвояване       | `T& operator=(T const& other)`               | `b = a;` след като и двете са инициализирани.                         |
| Деструктор                    | `~T()`                                       | Край на областта на действие; `delete`.                               |

> **Правило:** Ако обектът работи с динамична памет (или друг ресурс), пишеш и четирите. Ако имаш нужда от една — обикновено имаш нужда от всичките.

### Защо системните не са достатъчни?

**Системен конструктор за копиране** копира поле по поле. Ако едно от полетата е `char* name`, се копира *самият указател*, не съдържанието. Резултат:

```
Player a("Ivan");        // a.name → [памет за "Ivan"]
Player b(a);             // b.name → същата памет!

a и b сочат към една и съща памет.
Когато умре a → деструкторът освобождава паметта.
Когато умре b → деструкторът пак освобождава същата памет → катастрофа.
```

Това се нарича **двойно освобождаване (double free)** и е причина за труднооткриваеми бъгове.

### Пълна реализация на `Player` с Голямата четворка

```cpp
#include <cstring>

class Player {
    char* name;
    int   score;

    // Помощна функция — копира низа от източник в обекта
    void copyName(char const* src) {
        name = new char[strlen(src) + 1];
        strcpy(name, src);
    }

public:
    // 1) Конструктор по подразбиране — минимална памет, валидно състояние
    Player() : score(0) {
        name = new char[1];
        name[0] = '\0';
    }

    // (Бонус) Конструктор с параметри
    Player(char const* n, int s) : score(s) {
        copyName(n);
    }

    // 2) Конструктор за копиране — дълбоко копие
    Player(Player const& other) : score(other.score) {
        copyName(other.name);
    }

    // 3) Операция за присвояване
    Player& operator=(Player const& other) {
        if (this != &other) {              // 3.1 защита от a = a
            delete[] name;                  // 3.2 освобождаваме старата памет
            copyName(other.name);           // 3.3 заделяме нова и копираме
            score = other.score;
        }
        return *this;                       // 3.4 връщаме *this, за да работи a = b = c
    }

    // 4) Деструктор
    ~Player() {
        delete[] name;
    }

    char const* getName()  const { return name; }
    int         getScore() const { return score; }
};
```

Разлика **конструктор за копиране** vs **операция за присвояване**:

- **Конструктор за копиране** се вика върху *новосъздаван* обект — той още няма памет, която да се освобождава. Само заделя и копира.
- **Операция за присвояване** се вика върху *съществуващ* обект, който вече има памет. Затова стъпките са: освободи старото → заделени ново → копирай.

### Защита от самоприсвояване

```cpp
Player a("Ivan", 50);
a = a;   // ?!
```

Изглежда абсурдно, но в реален код се случва, особено когато имаш препратки/указатели и не виждаш веднага, че двата обекта са едно и също. Без проверката `if (this != &other)`, кодът на `operator=` би:
1. освободил `name` на `this` (което е и `name` на `other`);
2. опитал да копира от `other.name`, който вече е освободен → undefined behavior.

### Връщане на `*this` от `operator=`

`return *this;` връща препратка към текущия обект. Това позволява верижно присвояване:

```cpp
Player a, b, c;
a = b = c;   // еквивалентно на a = (b = c);
            // (b = c) връща b, после a = b
```

### Кратка интуиция за RAII

> Конструкторът придобива ресурс → деструкторът го освобождава. **Винаги**. Каквото и да се случи между тях.

# Въпрос 2

## 2.1 Принцип на наследяването

### Основната идея

Наследяването е механизъм за **създаване на нови класове чрез разширяване на съществуващи**. Производният клас (детето) "наследява" атрибутите и поведението на базовия (родителя), а после може да добавя свои.

Това отразява връзка от тип **"е" (is-a)** — например:

- Всеки `Hero` *е* `Player` (но не всеки `Player` е `Hero`);
- Всяко `Cat` *е* `Animal`;
- Всеки `Manager` *е* `Employee`.

`Hero` се описва с име, точки **и** магическа сила. Тоест `Hero` добавя само:
- новите полета (магическа сила);
- нови или допълнителни операции (използване на магия и т.н.).

Тази идея е първа реализирана през 1968 г. в езика Simula. Днес е във всички ООП езици.

### Защо ни е?

Три големи причини:
1. **Преизползване на код.** Не дублираш данните и операциите, които вече са в базовия клас.
2. **Изграждане на йерархии.** Можеш да работиш с различни типове обекти по унифициран начин (вижда се най-добре с полиморфизъм — следваща тема).
3. **Моделиране.** Често реалният свят е йерархичен ("животни → бозайници → котки") и наследяването е естественият начин да го изразиш.

### Различни видове наследяване (терминологично)

В лекциите се разграничават:
- **Наследяване на реализация** — наследниците споделят и данни, и (поне частично) реализация на функции. Пример: `Player` → `Hero`, `Bot`.
- **Наследяване на интерфейси** — наследниците споделят само сигнатурите, всеки има своя реализация. Пример: `Stack` → `ArrayStack`, `LinkedStack`.
- **Смесено наследяване** — комбинация от двете.

В тази тема ще се фокусираме на наследяване на реализация. Наследяването на интерфейси изисква виртуални функции, абстрактни класове и полиморфизъм — тема на следващи въпроси.

---

## 2.2 Синтаксис на наследяването

```cpp
class <име> : [<видимост>] <базов_клас> { 
    <тяло> 
};
```

`<видимост>` може да е `private`, `protected`, `public` (по подразбиране е `private`).

Примери:

```cpp
class Hero : public Player { /* ... */ };
class Derived : Base1, public Base2, protected Base3 { /* ... */ };   // множествено наследяване
```

В C++:
- Един базов клас **може да се наследи от много производни** (различни производни класове, имащи един и същ родител).
- Един производен клас **може да има много базови** (множествено наследяване — изисква специално внимание).

### Какво се случва при наследяване?

Производният клас **получава** от базовия:
- всички негови **член-данни**;
- всички негови **член-функции**;
- **достъп до `public` и `protected` компоненти**.

Производният клас **НЕ получава**:
- достъп до **`private` компонентите** на базовия (но *ги съдържа* във вътрешността си!);
- **приятелите** (`friend` декларациите) на базовия.

Производният клас **може** да дефинира свои член-данни и член-функции, **дори със същите имена** като в базовия. Това се нарича **предефиниране** (overriding) и не бива да се бърка с претоварването (overloading).

### Преобразуване на типове (upcasting)

Производният клас `D` се счита за **подтип** на базовия `B`:
- Всеки обект от `D` може да се разглежда като обект от `B` (защото има всичко, което има `B`, и още).
- Някой обект от `B` може и да не е `D` (защото `B` може да няма добавените от `D` неща).

Обекти, указатели и препратки от `D` се преобразуват към `B` **неявно**:

```cpp
Hero h("Asen", 100, 5);
Player p = h;        // ОК — Hero е Player (но се "отрязват" допълнителните полета — slicing!)
Player& pr = h;      // ОК — препратка не реже
Player* pp = &h;     // ОК — указател не реже
```

> ⚠️ Внимавай със **slicing** (рязане): копирането на `Hero` в обект от тип `Player` "отрязва" специфичните за `Hero` полета. За да работиш полиморфно — ползвай **препратки или указатели**.

### Пример

```cpp
class Player {
    char* name;
    int   score;
public:
    Player(char const* n, int s);
    // ... голяма четворка ...
    void print() const;
    int  getScore() const { return score; }
};

class Hero : public Player {
    int level;   // нова член-данна, специфична за Hero
public:
    Hero(char const* n, int s, int lvl);
    void print() const;        // предефинираме print
    int  getLevel() const { return level; }
};
```

`Hero` автоматично има `name`, `score`, `getScore()`, защото ги наследява от `Player` (като ги използва, разбира се, през публични методи — `private` полета не са достъпни директно).

## 2.3 Конструктори и деструктори при наследяване

### Основен принцип

> **Всеки конструктор се грижи директно само за инициализацията на член-данните на съответния клас.**

Производният клас **не пипа** наследените полета директно — той **делегира** инициализацията им на конструктора на базовия клас. Така:
- Не повтаряме код.
- Производният клас не зависи от това как точно е представен базовият.
- Ако базовият се промени, производният не е засегнат.

### Ред на изпълнение

При създаване на обект от производен клас:

1. Първо се вика конструкторът на **базовия** клас (инициализира наследената част).
2. После се инициализират член-данните на производния клас (в реда на деклариране).
3. Чак тогава се изпълнява тялото на конструктора на производния.

При унищожаване — **обратният ред**:

1. Изпълнява се тялото на деструктора на производния.
2. Унищожават се член-данните на производния (в обратен ред на деклариране).
3. Накрая се вика деструкторът на базовия.

> **Мнемоника:** *Конструкторите се викат отгоре надолу (от базата към наследника). Деструкторите — отдолу нагоре.*

### Синтаксис

```cpp
<производен-клас>::<производен-клас>(<параметри>)
    : <базов-клас>(<параметри>)
    [, <член-данна>(<параметри>) ]
{
    <тяло>
}
```

Пример:

```cpp
Hero::Hero(char const* n, int s, int lvl)
    : Player(n, s),    // викаме конструктора на базата
      level(lvl)        // инициализираме новото поле
{
    // тяло
}
```

**Ако пропуснем да инициализираме базовия клас**, автоматично се вика неговият **конструктор по подразбиране**. Това може да е сериозен проблем:

- Ако базовият клас няма конструктор по подразбиране → грешка по компилация.
- Ако базовият има конструктор по подразбиране, но той инициализира с "глупави" стойности (празно име, точки 0), наследената част на обекта остава в това състояние.

### Деструктори

Деструкторът на производния клас **не е нужно** да вика експлицитно деструктора на базата — това става **автоматично** след като приключи унищожаването на данните на производния. Просто пишеш своя деструктор, без да се притесняваш.

### Жизнен цикъл на обект от производен клас

1. Заделя се памет за обекта.
2. Извиква се конструктор, който:
   - извиква конструктор на базовия клас;
   - извиква конструктори на всички съдържани обекти-полета;
   - изпълнява собственото си тяло.
3. Работим с обекта.
4. Достига се края на областта на действие на обекта.
5. Извиква се деструктор, който:
   - изпълнява собственото си тяло;
   - извиква деструкторите на всички съдържани обекти-полета;
   - извиква деструктора на базовия клас.
6. Паметта на обекта се освобождава.

### Частни случаи — задачи за размишление

> Какво ще се случи, ако...
>
> ...в базовия клас **не е дефиниран нито един конструктор**:
> - в производния има дефиниран конструктор → не извикваш изрично базата → системният `Base()` се вика → ОК.
> - в производния няма дефиниран → системните и за двата → ОК.
>
> ...в базовия има дефиниран **поне един конструктор, но няма по подразбиране**:
> - в производния има дефиниран конструктор → ако не извикаш изрично друг конструктор на базата → грешка по компилация (липсва Base()).
> - в производния няма дефиниран → системен конструктор по подразбиране за производния → той опитва да вика Base() → грешка.
>
> Извод: ако базата има само конструктори с параметри, производният е длъжен явно да извика някой от тях.

## 2.4 Голямата четворка при производен клас

Накратко — какво трябва да правят:

### Конструктор за копиране

Конструкторът за копиране на производния клас е **обикновен конструктор**. Затова **трябва явно да извика конструктора за копиране на базата**, иначе се вика конструкторът по подразбиране!

```cpp
Hero::Hero(Hero const& other)
    : Player(other),   // ← ВАЖНО! Иначе се вика Player()
      level(other.level)
{ }
```

(Тук `Player(other)` работи, защото `other` е `Hero const&`, а `Hero` е подтип на `Player` → неявно преобразуване → вика се `Player::Player(Player const&)`.)

### Операция за присвояване

Тя е като всяка член-функция. **Трябва явно да извика в тялото си `operator=` на базата**, иначе наследените данни няма да се присвоят!

```cpp
Hero& Hero::operator=(Hero const& other) {
    if (this != &other) {
        Player::operator=(other);   // ← ВАЖНО! явно викане
        level = other.level;
    }
    return *this;
}
```

### Деструктор

Не е нужно да викаш `~Player()` ръчно — става автоматично.

```cpp
Hero::~Hero() {
    // ... твоят код (ако имаш свои ресурси)
}   // ~Player() се вика автоматично тук
```

### Системните

Ако не напишеш своя четворка, компилаторът генерира системна:
- **системен конструктор за копиране** — вика copy-конструктора на базата + copy-конструкторите на всички член-данни (поведение като при системния default).
- **системна `operator=`** — вика `operator=` на базата + `operator=` за всяко поле.

Когато базата работи коректно (без ресурси) или е дефинирала собствена голяма четворка — системните в производния често са ОК. Когато имаш свои ресурси (динамична памет в производния) — пишеш своя голяма четворка.

## 2.5 Достъп до наследените компоненти

### Спецификатори за достъп — преговор

Имаме два вида достъп:

- **вътрешен** достъп — от член-функции на класа и от **приятелски** функции (`friend`).
- **външен** достъп — от всякакви други функции (които не са член и не са приятели).

Вътрешният достъп е **винаги позволен**. Външният зависи от спецификатора:

| Спецификатор | Външен достъп                                    |
|--------------|--------------------------------------------------|
| `public`     | Неограничен                                      |
| `protected`  | Само от наследници                               |
| `private`    | Забранен                                         |

> Спецификаторът по подразбиране в `class` е `private`, в `struct` е `public`.

### Видимост при наследяване

Когато наследяваш, пишеш `class D : <видимост> B { ... };`. Тази видимост определя как **външният свят** ще вижда наследените компоненти.

| Достъп в B  | Наследяване | Външен достъп от D | Бележка                            |
|-------------|-------------|---------------------|-------------------------------------|
| `public`    | `public`    | `public`            | Най-чест случай                    |
| `public`    | `protected` | `protected`         | За наследници на D                 |
| `public`    | `private`   | `private`           | Само вътрешно                      |
| `protected` | `public`    | `protected`         | За наследници                      |
| `protected` | `protected` | `protected`         | За наследници                      |
| `protected` | `private`   | `private`           | Само вътрешно                      |
| `private`   | каквото и да е | забранен         | Никога не се вижда външно          |

С други думи: **наследяването може само да *стесни*, не и да разшири достъпа**.

`private` компонентите на базата винаги остават недостъпни външно — даже от методите на производния клас! Производният ги *съдържа* физически (те са част от обекта), но не може да ги пипа директно. Достъпва ги само през публичните или защитените методи на базата.

### Кога кое наследяване?

- **`public` наследяване** — стандартното, изразява връзка "is-a". `Hero` *е* `Player`. Външният свят знае, че `Hero` е вид `Player`. Това е почти винаги това, което искаш.
- **`protected` наследяване** — рядко. Производният клас и наследниците му виждат базата като своя, но външният свят не. Изразява "is-a, но скрито".
- **`private` наследяване** — изразява връзка "implemented-in-terms-of" (реализиран чрез). Производният класи преизползва механиката на базата, но **не е** базата отвън. Алтернатива е композиция (поле от тип `B`), която обикновено се предпочита.

### `protected` — за какво ни е?

Точно за наследяване. Полето е достъпно от методите на наследниците, но е скрито от външния свят.

```cpp
class Player {
protected:
    int score;   // наследниците могат да го пипат директно
public:
    int getScore() const { return score; }
};

class Hero : public Player {
public:
    void bonusPoints() {
        score += 100;   // ОК — protected се вижда от наследник
    }
};
```

Внимание: `protected` все пак е форма на излагане на вътрешни детайли. Чисто `private` + достъп през методи е по-капсулирано.

### Предефиниране (overriding) на наследени компоненти

В производния клас може да има компонент със **същото име** като в базата. Това е **предефиниране (overriding)** — да не се бърка с **претоварване (overloading)**.

- *Претоварване* — две функции в *един* клас с *едно и също име, но различни параметри*.
- *Предефиниране* — функция в производен клас със същата сигнатура като в базата.

Рядко се прилага за член-данни, основно за член-функции.

```cpp
class Player {
public:
    void print() const;
};

class Hero : public Player {
public:
    void print() const;   // предефинира Player::print
};
```

Сега при `Hero h; h.print();` се вика `Hero::print`. Ако искаме изрично да викнем версията на базата:

```cpp
void Hero::print() const {
    Player::print();        // явно викане през оператора ::
    std::cout << " (level " << level << ")";
}
```

> ⚠️ Внимание: предефинирането **не е виртуално** по подразбиране. При `Player* p = new Hero(...); p->print();` *ще се извика `Player::print`*, не `Hero::print`. Това се променя с виртуални функции — друга тема.

## 2.6 Капсулация и скриване на информацията

### Принцип на капсулацията

Идеята е да **разделим описанието от реализацията**:

- **Описание (интерфейс):** името на типа, сигнатурите на функциите и методите. *Какво* може да прави.
- **Представяне (имплементация):** полетата на типа, телата на функциите. *Как* го прави.

Капсулацията означава, че **външният код работи само с описанието**, не с представянето.

### Защо?

1. **Можем да подменим представянето, без да се отрази на потребителите.** Ако напишем `Rational` като `(int num, int den)` и после преминем към `(int num, unsigned den)` с допълнителни инварианти — кодът, който само вика `getNumerator()`, не трябва да се променя.

2. **Външните функции зависят само от описанието.** Това намалява свързаността (coupling) — модулите са по-независими.

3. **Промени по представянето не налагат промени по външните функции.**

4. **Описанието обикновено е по-просто от представянето** — изолира се сложността. Външният свят вижда само "лицето" на типа.

### Йерархично виждане

Можем да си мислим за слоеве (нива на абстракция). На ниво $n+1$ работим с описанието на ниво $n$. Представянето на ниво $n$ не зависи от представянията на нивата под него.

```
ниво n+1: пишем програма, която ползва Rational   <- работи с описанието
ниво n:   реализация на Rational чрез int          <- работи с описанието на int
ниво n-1: реализация на int                        <- ...
```

### Скриване на информацията

В C++ скриването се реализира чрез `private`/`protected`. Полетата задължително са `private` (или поне `protected` при наследяване с нужда от достъп). Външният достъп става единствено през публичните методи.

Това означава:
- **Никога не правиш полета `public`.** (Изключение: `struct`, ползвана като чист контейнер на данни, без инварианти.)
- **Винаги имаш ясно дефиниран интерфейс**: конструктори, селектори (`const` методи за четене), мутатори (методи за писане), операции, деструктор.

### Свързано: операция за указване на област (`::`)

Когато имаме областите (scope) на различни класове или пространства от имена, използваме оператора `::` за квалифициране на имената:

```cpp
Rational::print();   // print, дефинирана в класа Rational
std::cout;           // cout, дефиниран в namespace std
Player::operator=;   // operator= от Player
```

Това е особено важно при наследяване, когато искаме да викнем версия от базовия клас (`Player::print()` от `Hero::print()`).

## 2.7 Вложени класове

В C++ е разрешено да дефинираш клас вътре в друг клас.

```cpp
class List {
public:
    class Iterator {
        // ... реализация на итератор
    public:
        Iterator& operator++();
        int& operator*();
    };

    Iterator begin();
    Iterator end();

private:
    // ... вътрешно представяне
};
```

Извън класа достъпваш вложения с пълно име: `List::Iterator it = lst.begin();`.

### Кога ползваме вложени класове?

- Когато вложеният клас е тясно свързан с външния и няма смисъл сам по себе си (типичен пример — итератор за контейнер; възел на свързан списък/дърво).
- Когато искаме да ограничим видимостта на помощен клас.

### Особености

- Вложеният клас е като **отделен клас**, който живее в **областта на външния**. Той няма автоматичен достъп до полетата на външния клас (не е "вътрешност на обект от външния клас").
- Външният клас **може да достъпва** вложения според обичайните правила за достъп (ако е `public` — отвсякъде, ако е `private` — само вътрешно).
- Често вложеният клас се обявява за `friend` на външния (или обратното), за да получи специален достъп.

### Малко пример

```cpp
class LinkedList {
    struct Node {           // вложен клас, тук struct (public по подразбиране)
        int   data;
        Node* next;
        Node(int d, Node* n) : data(d), next(n) {}
    };

    Node* head;

public:
    LinkedList() : head(nullptr) {}
    
    void push_front(int x) {
        head = new Node(x, head);
    }
    
    ~LinkedList() {
        while (head) {
            Node* tmp = head;
            head = head->next;
            delete tmp;
        }
    }
};
```

Тук `Node` е вложен `struct` в `LinkedList`. Външният свят не вижда `Node` (защото `LinkedList::Node` е `private` по силата на `class` спецификатора, освен ако не го изнесем). Така представянето на списъка е скрито — типична капсулация.

## 2.8 Статични компоненти

### Статични член-данни

Статичните член-данни:
- **принадлежат на класа**, а не на отделните обекти;
- се **заделят еднократно** в областта за статични данни (не на стека, не в динамичната памет);
- са **споделени между всички обекти** на класа;
- декларират се с `static <тип> <име>;` вътре в класа;
- **дефинират се извън класа** (в .cpp файл) с пълно име: `<тип> <клас>::<име> = <израз>;`.

```cpp
// player.h
class Player {
    static int totalPlayers;   // декларация
    char* name;
public:
    Player(char const* n);
    ~Player();
    static int getTotalPlayers();
};

// player.cpp
int Player::totalPlayers = 0;   // ВАЖНО — дефиниция, заделя паметта

Player::Player(char const* n) {
    name = new char[strlen(n)+1];
    strcpy(name, n);
    ++totalPlayers;   // увеличаваме броя
}

Player::~Player() {
    delete[] name;
    --totalPlayers;
}
```

> **Интуиция:** Статичните полета са като глобални променливи, но "поставени" вътре в класа, така че да имат логическа връзка с него.

### Статични член-функции

Статичните член-функции:
- **не се нуждаят от обект**, за да бъдат извикани;
- **не получават `this`** като скрит параметър;
- имат **вътрешен достъп до статичните член-данни и член-функции**;
- **нямат достъп до нестатичните** член-данни и член-функции (защото няма обект, на който да принадлежат).

```cpp
class Player {
    static int totalPlayers;
public:
    static int getTotalPlayers() {
        return totalPlayers;     // ОК — статично поле
        // return score;         // ГРЕШКА — нестатично, няма this!
    }
};

// Викане без обект:
int n = Player::getTotalPlayers();

// Или през обект (също работи, но не е препоръчително — заблуждаващо е):
Player p("Ivan");
int m = p.getTotalPlayers();   // ВСЕ ОЩЕ не ползва p — поведението е същото
```

### За какво ги ползваме?

- **Брояч на инстанции** (както в примера).
- **Константи на класа.** Например `static const int MAX_SIZE = 100;`.
- **Утилити функции, които концептуално принадлежат към класа**, но не оперират върху конкретен обект. Например `static Date Date::today();` — фабричен метод.
- **Споделени ресурси.** Един пул, един кеш, един сингълтон.

### Особености при инициализация

- Не можеш да инициализираш статично поле в инициализиращия списък на конструктор (защото то не принадлежи на обект).
- Стойността на интегрален статичен `const` може да се зададе вътре в класа: `static const int N = 100;`. За други типове — извън класа.

### Сравнение: нестатични vs статични

| Свойство                      | Нестатично                 | Статично                              |
|-------------------------------|-----------------------------|----------------------------------------|
| Принадлежи на                 | конкретен обект             | целия клас                             |
| Място в паметта               | в обекта (стек/heap)        | област за статични данни               |
| Брой копия                    | по едно на обект            | едно общо                              |
| `this` параметър              | да                          | няма                                   |
| Достъп до нестатични членове  | да                          | не (няма обект)                        |
| Викане                        | `obj.method()`              | `Class::method()`                      |

# Приложение А: Цялостен пример

Свързваме почти всичко в един обозрим пример.

```cpp
#include <cstring>
#include <iostream>

// Базов клас
class Player {
protected:
    char* name;
    int   score;
    
    static int totalPlayers;   // брой създадени играчи
    
    void copyName(char const* src) {
        name = new char[strlen(src) + 1];
        strcpy(name, src);
    }
    
public:
    // Конструктор по подразбиране
    Player() : score(0) {
        name = new char[1];
        name[0] = '\0';
        ++totalPlayers;
    }
    
    // Конструктор с параметри
    Player(char const* n, int s) : score(s) {
        copyName(n);
        ++totalPlayers;
    }
    
    // Конструктор за копиране
    Player(Player const& other) : score(other.score) {
        copyName(other.name);
        ++totalPlayers;
    }
    
    // Операция за присвояване
    Player& operator=(Player const& other) {
        if (this != &other) {
            delete[] name;
            copyName(other.name);
            score = other.score;
        }
        return *this;
    }
    
    // Деструктор
    ~Player() {
        delete[] name;
        --totalPlayers;
    }
    
    // Селектори
    char const* getName()  const { return name;  }
    int         getScore() const { return score; }
    
    // Мутатори
    void setScore(int s) { score = s; }
    
    // Операции
    void print() const {
        std::cout << "Player: " << name << ", score: " << score;
    }
    
    // Статичен метод
    static int getTotalPlayers() { return totalPlayers; }
};

// Дефиниция на статичното поле — задължителна!
int Player::totalPlayers = 0;


// Производен клас
class Hero : public Player {
    int level;
    
public:
    Hero(char const* n, int s, int lvl)
        : Player(n, s), level(lvl) { }
    
    Hero(Hero const& other)
        : Player(other), level(other.level) { }
    
    Hero& operator=(Hero const& other) {
        if (this != &other) {
            Player::operator=(other);   // не забравяй базата!
            level = other.level;
        }
        return *this;
    }
    
    // деструкторът — не дефинираме, системният работи (no own resources)
    
    int getLevel() const { return level; }
    
    void levelUp() { ++level; }
    
    // Предефиниране
    void print() const {
        Player::print();    // викаме версията на базата
        std::cout << " (level " << level << ")";
    }
};


int main() {
    Player p("Asen", 100);
    Hero   h("Ivan", 50, 3);
    
    p.print();   std::cout << '\n';
    h.print();   std::cout << '\n';
    
    Hero h2 = h;       // copy constructor
    h2.levelUp();
    h2.print();        std::cout << '\n';
    
    std::cout << "Players alive: " << Player::getTotalPlayers() << '\n';
    
    return 0;
}
```

**Очакван изход:**

```
Player: Asen, score: 100
Player: Ivan, score: 50 (level 3)
Player: Ivan, score: 50 (level 4)
Players alive: 3
```

# Приложение Б: Какво да очаквам като въпроси

Когато изпитващият те пита по тези теми, чести подвъпроси са:

- *Каква е разликата между `struct` и `class`?* (По подразбиране достъп — `public` срещу `private`. Иначе са еквивалентни.)
- *Защо конструкторът за копиране приема параметър по препратка?* (За да не извика себе си рекурсивно.)
- *Какво е разликата между конструктор за копиране и операция за присвояване?* (Първият създава нов обект; вторият заменя съдържанието на съществуващ. Затова присвояването първо освобождава старата памет.)
- *Защо в `operator=` имаме проверка `if (this != &other)`?* (Защита от самоприсвояване — иначе освобождаваме нашата собствена памет, а после копираме от вече освободена памет.)
- *Какво е RAII?* (Ресурсите се придобиват в конструктор и се освобождават в деструктор. Гарантира надеждно освобождаване, дори при изключения.)
- *Кои са Голямата четворка и кога ги пишем?* (Конструктор по подразбиране, конструктор за копиране, оператор за присвояване, деструктор — когато обектът управлява външни ресурси.)
- *Какъв е редът на викане на конструкторите при наследяване?* (Първо базата, после полетата на производния, после тялото на конструктора на производния. Деструктори — в обратен ред.)
- *Какво се случва с private членовете на базата при наследяване?* (Производният ги съдържа физически, но няма достъп до тях директно.)
- *Защо `protected` е "междинно" между `public` и `private`?* (Достъпно от наследниците, но не отвън.)
- *С какво се различава предефиниране (overriding) от претоварване (overloading)?* (Overloading — едно име, различни параметри в един клас; overriding — едно име в производен клас, което скрива името от базата.)
- *Защо инициализиращ списък, а не присвояване в тялото?* (Едно действие вместо две; единственият начин за `const`, препратки, обекти без default constructor, и за викане на конструктор на база.)
- *Каква е разликата между статични и нестатични член-функции?* (Статичните нямат `this`, не работят с конкретен обект, имат достъп само до статичните компоненти.)
